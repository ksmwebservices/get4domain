# Dispatch report P10: plumberboy.get4domain.com answered 404 with no rewrite header

Branch `v3-pub-fe18` (from `v3-pub-fe17`). Not pushed. No .env read, no real service called (a fake backend on 127.0.0.1 only; every `*.get4domain.com` name is mapped to 127.0.0.1 inside the test browser), no server touched. Backend read only: `get4domain-w2/backend-api/src/site-domains/settings` (reserved names).

## Exact cause (P10.1)
With the live settings, `MAIN_HOST=v3site.get4domain.com` and the vendor host `plumberboy.get4domain.com`:
1. `middleware.ts` runs `hostLayer(req)` first (host layer is on: `V3_PUBLIC_ENABLED=true` and `MAIN_HOST` set). It calls `decideHost` (`host-routing.ts`) which calls `classifyHost` (`lib/v3-public/hostnames.ts`).
2. `classifyHost` took the **vendor base domain from MAIN_HOST**: `baseDomain(cfg)` = `v3site.get4domain.com`. Then, at **`hostnames.ts:95` (before P10): `if (!h.endsWith(\`.${base}\`)) return { kind: 'unknown' };`**. `plumberboy.get4domain.com` does not end with `.v3site.get4domain.com`, so it is class **unknown**. (A name under the portal host, `plumberboy.v3site.get4domain.com`, would have been a vendor, which is why the V3 portal tests always looked fine.)
3. `decideHost` has `default: return { action: 'not-found', host: 'unknown' }` (`host-routing.ts`), and the middleware answers it at **`middleware.ts:108` (before P10): `if (d.action === 'not-found') return { done: plainNotFound() };`**: a plain 404, `x-robots-tag: noindex`, no rewrite header, no title. That is the live answer. The function that rewrites to `/site/<name>` (`vendorHostRewrite`, which does use `NEXT_PUBLIC_SITE_BASE_DOMAIN`) is never reached because `hostLayer` has already answered.
4. **P9's belief was wrong** ("the host is parsed correctly"): it ran with the flag off and no `MAIN_HOST`, where `hostLayer` returns null and only `vendorHostRewrite` runs.

Reproduced by calling the real `middleware()` with a `NextRequest` and the exact live settings (`__tests__/p10.test.ts`). **Run against the old middleware, the live case failed exactly as live**: status 404, no `x-middleware-rewrite`; 9 of 14 tests failed (the 4 live-case tests, the reserved-prefix tests, the "contains v3" test and the 3 log tests), while the portal-host tests (v3site, v3directory, v3app/api/admin/media 404, www 308) passed on the old code, so they are a true baseline.

**What is evaluated at BUILD time in the middleware (edge) bundle:** exactly one value, `process.env.NEXT_PUBLIC_SITE_BASE_DOMAIN`, read as a static member (`middleware.ts:44`, `const SITE_BASE = ...`, and the same static read now in `hostnames.ts explicitSiteBase`). The build inlines it (`get4domain.com`). Everything else is read from the runtime environment on each request: `readHostConfig()` reads `MAIN_HOST`, `DIRECTORY_HOST`, `APP_HOST`, `API_HOST`, `ADMIN_HOST`, `MEDIA_HOST`; `isV3PublicEnabled` and `useMocks` read their flags; `apiBase()` reads `INTERNAL_API_URL`. The old host classifier ignored the build-time base domain and used the runtime `MAIN_HOST` instead; that mismatch is the bug. (`DEMO_ACCESS_SECRET` is a static non-public read, also runtime.)

## What changed (P10.2)
- `hostnames.ts`: `HostConfig.vendorBase` (the vendor base domain, `NEXT_PUBLIC_SITE_BASE_DOMAIN`). `classifyHost` matches the portal hosts exactly first (main, www of main, directory, app, admin, api, media), then treats any single-level `<name>.<base>` that is not reserved as a vendor host, under the vendor base **and** (as before) under the main host. Case, port and a trailing dot are handled by `normalizeHost`. The middleware passes `vendorBase: SITE_BASE` (the build-inlined setting, default `get4domain.com`) to `hostLayer`, `vendorHostRewrite` and the log, so `readHostConfig()` alone still means "nothing set, nothing classified".
- **Reserved names** = union of: the frontend list (www, app, admin, api, gapi, directory, media, mail, send and the nine V2 client names), the backend's `MANDATORY_RESERVED_SUBDOMAINS` (adds `partner`), the backend's default `reservedSubdomains` setting (login, dashboard, support, staging, demo, cdn, static, portal, get4domain, g4d, ...), plus every name starting `v3` or `t3-`. A name that only contains v3 or t3 (`pv3`, `cat3-shop`) is a vendor. Portal hosts keep their behaviour exactly (tests above).
- **Second defect found while running the browser script:** the generic design's links point at `/site/<name>/...`; Next prefetches them on the vendor host, and with the host layer on the middleware answered those with a plain 404 (it only rewrote `/` paths), so the requests hung. A vendor host now passes through its **own** `/site/<name>` and `/site/<name>/...` as they are, and a `/site/<other>` path is still a 404 (a vendor host never shows another vendor's site). Tests for both.
- P8 and P9 behaviour is unchanged (Free information page, Pro and unknown-industry generic design, "being set up", not-found, runtime API address). Checked again in the browser.
- `scripts/v3-public/hooks.mjs`: maps `next/server` to its `.js` entry so the test runner can load the real middleware.

## Log line (P10.3)
One `console.warn` JSON line `{"evt":"host_not_rewritten","host":"...","class":"...","reason":"..."}` whenever a request is not sent to a vendor site. Reasons: `PORTAL_HOST` (main, directory, app, admin, api, media hosts), `RESERVED_NAME` (a reserved or v3/t3- name under the base), `EMPTY_SUBDOMAIN` (the bare base domain, or a name that is not a single label), `NOT_UNDER_BASE` (any other host). Host, class and reason only: no path, query, cookie or person. A host that is not a valid name is logged as `invalid`. The same host and reason is written once per ten minutes per server process (so a busy portal host does not flood the log). The P9 `vendor_not_found` lines stay.

## Choices
- The vendor base domain keeps the default `get4domain.com` only in the middleware (as it always did); `readHostConfig()` does not invent one.
- Names under the portal main host (`x.v3site.get4domain.com`) stay vendor hosts as before.
- Log throttling is per process and capped at 500 keys.

## For the owner
- After deploy, a request for any `<name>.get4domain.com` that is not a portal or reserved host goes to the vendor renderer; if the vendor is not a V3 site and not a V2 site it shows the normal not-found page, with `vendor_not_found` and the reason in the log.
- A vendor named like a reserved word (login, support, ...) can never be served (the backend refuses to register them too).
- Nginx must send `*.get4domain.com` to this container for the vendor names to reach it; the container does the rest.
